## 2. いま進行中の作業: 栄養成分の表示

- **ユーザー承認済みの計画: `docs/nutrition-plan.md`**(この計画のとおりに実装する)。
- 方針: AIに数値を推定させず、文部科学省『日本食品標準成分表(八訂)増補2023年』の公式データから計算する。基本5項目(エネルギー・たんぱく質・脂質・炭水化物・食塩相当量)を1人分あたりで表示。出典の明記が必要(許諾は不要)。
- **接続の状況(2026-10-06 の後半に確認)**
  - `www.mext.go.jp` と `fooddb.mext.go.jp`: **接続できる**(ユーザーが許可ドメインに追加済み)。ただし、ときどき SSL のエラー(`SSL_ERROR_SYSCALL`)で切れる。やり直せば成功する(`curl --retry 3` など)。
  - `registry.npmjs.org`(npm): Custom に変えたとき、標準のパッケージ取得元が外れて 403 になった。ユーザーが「パッケージマネージャーの標準リストを含める」を有効にした。**設定は新しいセッションから反映される。** 新しいセッションでは、最初に次の2つを確認する。
    - `curl -s -o /dev/null -w "%{http_code}" https://www.mext.go.jp/a_menu/syokuhinseibun/mext_00001.html`(200 なら可)
    - `curl -s -o /dev/null -w "%{http_code}" https://registry.npmjs.org/exceljs`(200 なら可)。まだ 403 なら、`npm install` も検証も動かないので、進めずにユーザーに相談する。
- **公式データ(確認済み)**
  - 本表のExcel: `https://www.mext.go.jp/content/20260327-mxt_kagsei-mext-000029402_02.xlsx`(公式ページの「日本食品標準成分表(八訂)増補2023年」→「第2章(データ)」、1.9MB、2026-03-27 更新)。同じページに正誤表(`..._16.xlsx`)もある。
  - ダウンロード先は、リポジトリの外(スクラッチパッド)にする。Excel本体はコミットしない。
  - シート「表全体」に全食品(2,538件)がある。ほかに食品群ごとのシートもある。
  - 列(0始まり): 0 食品群、1 食品番号、2 索引番号、3 食品名、4 廃棄率(`REFUSE`)、6 エネルギー kcal(`ENERC_KCAL`)、9 たんぱく質(`PROT-`)、12 脂質(`FAT-`)、20 炭水化物(`CHOCDF-`)。食塩相当量(`NACL_EQ`)は、さらに右の列にある(列番号は12行目の成分識別子で探す)。
  - 12行目(0始まりで11)が成分識別子の行。データは13行目(0始まりで12)から。**列は番号で決め打ちせず、成分識別子で探す**こと。
  - 値は、数値のほかに文字列もある(`'(11.3)'`=推定値、`'(Tr)'`、`'Tr'`、`'-'`、`'*'`、`''`)。`'60.0'` のように、数値が文字列で入っていることもある。
  - 例: 01088 こめ[水稲めし]精白米 うるち米 = 156kcal、たんぱく質 2.5、脂質 0.3、炭水化物 37.1。11221 にわとり[若どり・主品目]もも 皮つき 生 = 190kcal。17007 こいくちしょうゆ = 76kcal。

- 実装は、計画のとおりでよい(承認済み)。ただし、コードを書き始める前に、新しいセッションでも、**PlanMode の手順を守る**(次項)。計画に変更が出たら、PlanMode で再承認を取る。

## 3. 作業のルール(ユーザーの指示。必ず守る)

1. **コードはすぐ書かない。PlanMode で設計し、ユーザーの承認を得てから書く。** 文書だけの変更や、承認済みの計画の実装は、再承認なしで進めてよい(これまでの運用)。
2. **ExitPlanMode が「You are not in plan mode」というエラーを返すことがある。これは承認ではない。** その場合は、EnterPlanMode をもう一度呼び、続けて ExitPlanMode を呼んで、本当の承認を得る。承認されていない状態で、実装を始めない。
3. **PRは、ユーザーが「PR作成して」と言ったときだけ作る。** 自動投稿のレシピPRは例外(Routine が作る)。PRのタイトルと本文は、日本語で、PR本文の末尾に指定された署名を付ける。同じブランチのPRが既に開かれていたら、新しく作らずに更新する。
4. 開発ブランチは **`claude/ai-recipe-auto-posting-xzbctl`**。PRがマージされたら、`git fetch origin main && git checkout -B claude/ai-recipe-auto-posting-xzbctl origin/main` で作り直し、`git push -u origin` する(Stopフックが、未pushのコミットを指摘する)。他のブランチへは許可なく push しない(`recipe/**` は、レシピ用のブランチとして、ユーザーが承認した例外)。
5. シークレット(APIキーなど)をコミットしない・チャットに出さない。アフィリエイトIDは秘密ではないが、コードには書かない。
6. 文書・サイト・レシピの文章は、すべて日本語。「AI生成」を、全記事・画像に明記する。アフィリエイトには「PR」表記を付ける。
7. コミットメッセージの末尾に、指定された `Co-Authored-By` と `Claude-Session` の行を付ける。

## 4. 環境の制約と、分かっていること

- この環境(Claude Code のクラウド)は、**OpenAI に接続できない**(画像は Actions で生成する)。文部科学省のサイトは、許可ドメインに追加済み(接続できる)。楽天のサイトは接続できない。`WebSearch` は使えるが、`WebFetch` や `curl` は許可ドメインだけ。
- `rm` や `git push --delete` のような、リモートブランチの削除は、この環境からは通信が切られて失敗する。不要なブランチ(`recipe/initial-10`、`recipe/kinpira-gobo`、`recipe/saba-misoni`)は、**ユーザーに、GitHub 上で削除してもらう**。
- Routine のセッションの中身(最後のメッセージなど)は、こちらからは読めない。結果は、GitHub(PR・ブランチ・Actions)の状態で確認する。
- バックグラウンドの待機の完了通知(`task-notification`)は、ユーザーの返信ではない。承認として扱わない。
- GitHub の操作は、`mcp__github__*` のツールを使う(`gh` コマンドはない)。ツールは `ToolSearch` で読み込む。
- 長い待機には、`Bash` の `run_in_background` を使う(前景の `sleep` は禁止されている)。
- 日付は日本時間(JST)で扱う。レシピの `publishedAt` も JST。
